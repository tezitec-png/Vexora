# Architecture

A map of how Vexora works under the hood, for whoever forks it.

## Request flow (production)

```
browser
  └─ Cloudflare Pages (project vexorium, advanced mode)
       ├─ static assets  → protected/ (obfuscated build of public/)
       └─ EVERY request hits _worker.js first (run_worker_first)
            ├─ /api/*, /admin/api/*  → server logic (server/worker.js)
            ├─ /cfw/bases/*          → 403 (firmware bases are private)
            └─ everything else       → env.ASSETS.fetch (static file)
```

`protected/` is generated by `node build-protect.js`: it bundles `public/` + an obfuscated `server/worker.js` into one deployment folder. **Never edit `protected/`** — edit the sources and rebuild.

## The worker

`server/worker.js` is a single vanilla-JS file (~3.5k lines). No framework. Sections:

1. **Boot/middleware**: origin checks (same-origin required for mutations), cookie helpers, JSON body reader with size caps, rate limiter (`chatBucket(key, max, windowMs)`), admin-token auth (`exp + hex(HMAC-SHA256(SHA256("vexora-admin-key:"+pwd)))`), rider-token auth (`riderFromReq`), bot-secret auth.
2. **Schema**: `ensureSchema(env)` runs once per isolate; creates every table + index with `IF NOT EXISTS`, then backfills/migrates columns via safe `ALTER TABLE` inside try/catch. Adding a feature = add the `CREATE TABLE`/`ALTER` here and it migrates in production automatically on the next deploy.
3. **Public site APIs**: health (`maint` flag), feature flags (5 s isolate cache), stats/events ingestion (90-day retention), feedback, firmware build endpoints (TEA container assembly, all in-memory, guardrails enforced server-side).
4. **Support console APIs**: Discord OAuth callback, console tokens, chat sessions, message send/poll/read-receipts, photo/audio upload to R2, Web Push, translation (Groq, async via `waitUntil` with graceful fallback).
5. **Rider APIs**: stepwise signup with IP-based anti-raid limits (D1 `rider_reg_ip`), email verify/reset (Resend; stub mode when the key is a test value), login + lockout, profile (bio 160 chars, hex color, avatar), DMs (30-day retention, photo notes, `\u0001pic:{id}` markers), account export & GDPR delete (cascading).
6. **Community APIs**: feed (For you / Following / weekly Top), posts to R2 (100/rider cap, 10/day), likes (double-tap aware), comments with one-level replies, comment likes (liked-first ordering), follows (`fing` state included per feed row), profiles, follower/following lists, notifications (bell, 30-day retention, seen-marking), view counts, reports (Discord-style reasons + Groq severity verdict stored in the admin queue).
7. **Admin APIs**: dashboard data, rider list + codes viewer, reports queue, IP rules, flags, GDPR tools.

## D1 schema (main tables)

| Table | Purpose | Notes |
|---|---|---|
| `events` | Visit/build analytics | 90-day purge, indexed by `ts` |
| `flags` | Feature flags | edited live from admin |
| `chat`, `chat_msg` | Support chat sessions/messages | indexed by session |
| `rider`, `rider_dm`, `rider_dm_msg`, `rider_pic` | Rider accounts + DMs + media markers | `rider_dm(a,b,id)` index; photos live in R2, message holds `\u0001pic:{key}` |
| `rider_reg_ip`, `lockout` | Anti-raid counters | 3 signups/6h/IP; login lockout |
| `rider_report` | Reports queue | `why = "reason | detail"`, AI verdict JSON |
| `comm_post`, `comm_like` | Feed posts + likes | likes PK `(post,rid)`; `comm_post(rid,id)` index |
| `comm_comment` | Comments + replies (`parent`) | `(post,id)` index |
| `comm_cmt_like` | Comment likes | PK `(comment,rid)` |
| `comm_follow` | Follow graph | PK `(rid,target)` + `(target,rid)` index (the feed's "do-you-follow" subquery is per-row) |
| `comm_profile` | Bio/color/avatar | avatar key points to R2 |
| `comm_notif` | Activity notifications | kinds: like, comment, follow, clike; `(rid,seen,id)` index |
| `comm_cmt_like` purges | GDPR + comment delete | cascading |

## R2 layout (`BUCKET`)

- `comm/<key>` — feed photos (permanent until author/admin delete)
- DM photos & voice notes — keys referenced from `rider_dm_msg`
- Avatars — referenced from `comm_profile.avatar`
- All media served through authenticated worker routes (`/api/comm/media/:key`, `/api/pic/:id` — the latter 401s without a valid session), never public buckets.

## Frontend

- **`index.html`** — the app: tuning studio, feedback, rider tab (signup wizard + rider directory + DMs), community tab entry. Vanilla JS modules in `assets/` (`app.js`, `i18n.js`, `tire.js`, `sim.js`, `chat.js`, `live.js`, `polish.js`…).
- **`community.html`** — the feed: single-file page, 100dvh scroll-snap slides locked to 9:16, black+green theme, TikTok-style comment sheet, long-press deletion, swipe gestures, service-worker-cached.
- **`support.html`** — agent console. **`admin.html`** — admin dashboard.
- **i18n**: `assets/i18n.js` holds 5 language packs; a parity test asserts every key exists ×5.
- **Service worker**: versioned cache (`vexora-17xx`); bump the version string to force clients to refresh assets.

## Design system (what the founder enforced)

- Montserrat only. Black/white chrome; the community feed may use green accents + the red active heart; auth buttons blue; white for the feed CTA. Blue was banned everywhere else by design taste — respect it or make it yours, deliberately.
- One primary action per screen; step subtitles so users know where they are; no stacked forms.
- Landing stays short. Tabs at the bottom on mobile.
